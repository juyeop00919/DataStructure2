# 과제 14: 힙 정렬, 퀵 정렬 및 병합 정렬의 성능 비교 분석

## 1. 실험 개요 및 환경
본 실험에서는 무작위 정수 배열에 대하여 대표적인 $O(n \log n)$ 정렬 알고리즘인 **힙 정렬(Heap Sort)**, **병합 정렬(Merge Sort)**, **퀵 정렬(Quick Sort - First, Random, Median-of-Three)**을 수행하고, 데이터 크기($n = 1,000 \sim 20,000$)에 따른 **숫자 비교 횟수, 실행시간, 최대 추가 메모리 사용량**을 비교·분석하였다.

- **데이터 크기 ($n$)**: 1,000 / 2,000 / 4,000 / 8,000 / 16,000 / 20,000
- **데이터 조건**: `0 ~ 99,999` 범위의 무작위 정수 (중복 허용, 모든 알고리즘에 동일한 원본 배열 복사본 사용)
- **측정 방식**: 실행시간의 미세 오차를 줄이기 위해 각 데이터 크기별로 **1,000회 반복 실행한 평균값**을 산출하였으며, 운영체제 및 아키텍처는 64비트(포인터 8 Bytes, `int` 4 Bytes) 환경을 기준으로 측정하였다.

## 3. 항목별 상세 비교 및 원인 분석

### [1] 데이터 크기 증가에 따른 세 정렬 알고리즘의 비교 횟수 변화
- **공통 추세 ($O(n \log n)$ 증가)**: 데이터 크기 $n$이 2배씩 증가할 때($1,000 \to 2,000 \to 4,000 \to 8,000 \to 16,000$), 세 알고리즘 모두 비교 횟수가 약 **2.15 ~ 2.25배**씩 증가하였다. 이는 $2n \log_2(2n) = 2(n \log_2 n + n)$ 수식에 따른 전형적인 $O(n \log n)$ 증가 추세이다.
- **알고리즘 간 비교 횟수 순위 (`Merge Sort < Quick Sort < Heap Sort`)**:
  1. **병합 정렬 (`260,863`회 @ $n=20,000$)**: 배열을 절반($n/2$)으로 분할하여 트리의 높이가 최소($\lceil \log_2 n \rceil$)로 유지되며, 병합 시 원소 하나를 확정할 때마다 1회의 비교만 수행한다. 이론적 비교 횟수인 $n \log_2 n - 1.26n \approx 260,554$회와 거의 일치하며 세 알고리즘 중 비교 횟수가 가장 적다.
  2. **퀵 정렬 (`319,505 ~ 340,494`회 @ $n=20,000$)**: 피벗이 매번 정중앙에 위치하지는 않으므로 분할 트리의 평균 높이가 병합 정렬보다 약간 높다(이론적 평균 $\approx 1.39n \log_2 n$). 따라서 병합 정렬보다 약 22~30% 많은 비교가 발생하였다.
  3. **힙 정렬 (`510,726`회 @ $n=20,000$)**: 비교 횟수가 병합 정렬의 약 **1.96배**, 퀵 정렬의 약 **1.5 ~ 1.6배**로 가장 많았다. 이는 힙 정렬의 구조적 특성 때문이다. 정렬 단계에서 루트(최댓값)를 말단 리프 노드의 작은 값과 교환한 뒤 `heapify`를 수행할 때, 그 작은 값이 다시 트리의 바닥 근처까지 내려가면서 **매 층(Level)마다 왼쪽 자식과 오른쪽 자식 모두와 값을 비교(층당 2회 비교)**해야 한다. 결과적으로 초기 힙 구성($O(n)$)과 추출 과정($\approx 2n \log_2 n$)이 합쳐져 약 $2n \log_2 n - 3n$회의 비교가 발생한다.

### [2] 힙 정렬, 병합 정렬, 퀵 정렬의 실행시간 차이
- $n = 20,000$ 기준 실행시간은 **Quick (First: `1.8580ms`) $\approx$ Quick (Median3: `1.9000ms`) $<$ Merge Sort (`1.9260ms`) $<$ Quick (Random: `2.1340ms`) $<$ Heap Sort (`2.7880ms`)** 순으로 나타났다.
- **퀵 정렬이 비교 횟수가 더 많은 병합 정렬보다 빠른 이유**:
  - 병합 정렬은 비교 횟수가 가장 적지만, 매 단계마다 정렬 결과를 임시 배열(`temp`)에 기록한 뒤 다시 원본 배열(`arr`)로 복사하는 **추가적인 메모리 읽기/쓰기 오버헤드**가 발생한다.
  - 반면 퀵 정렬은 원본 배열 내에서 인접한 인덱스를 순차적으로 스캔하며 필요한 경우에만 `swap`을 수행하므로 **참조 지역성(Locality of Reference)**이 뛰어나고 데이터 이동 비용이 적어 실제 실행시간이 가장 빠르다.
- **힙 정렬의 실행시간이 가장 느린 이유**:
  1. **비교 및 교환 연산량**: 매 추출 단계마다 작은 원소를 루트에 올렸다가 리프 노드까지 끌어내리므로 비교 횟수(`510,726`회)와 `swap` 횟수가 모두 많다.
  2. **낮은 캐시 지역성 (Cache Locality 저하)**: 배열 인덱스를 순차적으로 접근하는 병합·퀵 정렬과 달리, 힙 정렬은 부모 인덱스 $i$에서 자식 인덱스 $2i+1$, $2i+2$로 메모리 주소를 계속 건너뛰며 접근한다. 데이터 크기가 커질수록 CPU L1/L2 캐시 히트율(Cache Hit Ratio)이 낮아져 실행시간이 가장 길어진다.

### [3] 세 정렬 알고리즘의 메모리 사용량 차이
- $n = 20,000$ 기준 추가 메모리 사용량은 **Heap Sort (`80 Bytes`) $\ll$ Quick Sort (`900 ~ 1,620 Bytes`) $\ll$ Merge Sort (`80,704 Bytes`)** 순으로 차이를 보였다.
- **힙 정렬 ($O(1)$, `80 Bytes`)**: 별도의 배열이나 재귀 호출 없이 입력 배열 자체를 힙으로 간주하여 반복문 기반 `heapify`로 정렬하는 **제자리 정렬(In-place Sort)**이다. 데이터 크기 $n$이 1,000에서 20,000으로 커져도 보조 변수와 단일 함수 호출 스택 프레임인 `80 Bytes`만 일정하게 사용한다.
- **퀵 정렬 ($O(\log n)$, `576 ~ 1,620 Bytes`)**: 추가 배열은 사용하지 않으나 분할 정복을 위한 재귀 호출 스택이 필요하다. 데이터 크기가 20배 증가할 때 메모리 사용량은 로그 스케일에 비례하여 완만하게 증가하였다.
- **병합 정렬 ($O(n)$, `4,484 ~ 80,704 Bytes`)**: 병합 결과를 저장하기 위해 원본 배열과 동일한 크기의 동적 할당 임시 배열(`n * sizeof(int)`)이 필수적이다. $n = 20,000$일 때 임시 배열만 `80,000 Bytes`를 차지하여 힙 정렬 대비 **약 1,008배**, 퀵 정렬 대비 **약 50~90배** 많은 메모리를 소비하였다.

### [4] 퀵 정렬의 피벗 선택 방법에 따른 성능 차이
1. **세 원소의 중앙값 선택 (`Quick (Median3)`)**:
   - **비교 횟수 및 메모리 최적**: $n = 20,000$에서 비교 횟수(`319,505`회)와 메모리 사용량(`900 Bytes`, 최대 재귀 깊이 25) 모두 퀵 정렬 3종 중 가장 우수하였다. 양 끝과 중앙 원소 중 중간값을 피벗으로 선택함으로써 불균형 분할(Worst-case split)을 방지하고 재귀 트리의 균형을 안정적으로 유지했기 때문이다.
   - **실행시간**: 피벗 선택 시 최대 3회의 추가 비교 연산이 수행되지만, 분할 균형 이득으로 상쇄되어 `Quick (First)`와 거의 동일한 속도(`1.9000ms`)를 기록하였다.
2. **첫 번째 원소 선택 (`Quick (First)`)**:
   - 입력 데이터가 무작위(Random)로 생성되었기 때문에 첫 번째 원소를 선택해도 평균적으로 무작위 피벗과 유사한 분할 성능을 보였으며, 피벗 선택을 위한 추가 연산(난수 생성이나 중앙값 비교)이 없어 실행시간(`1.8580ms`)이 미세하게 가장 빨랐다. (단, 이미 정렬된 데이터가 입력될 경우 $O(n^2)$ 및 스택 오버플로우로 성능이 급락하는 한계가 존재한다.)
3. **무작위 원소 선택 (`Quick (Random)`)**:
   - **실행시간 저하 (`2.1340ms`)**: 매 분할(Partition) 호출마다 `rand()` 함수를 호출하고 나머지 연산(`%`)을 수행하는 오버헤드가 누적되어 `First` 및 `Median3`보다 약 12~15% 느리게 측정되었다.
   - **최대 메모리 증가 (`1,620 Bytes`)**: `First`와 `Median3`는 결정론적(Deterministic) 알고리즘이므로 동일한 배열에 대해 1,000회 반복해도 재귀 깊이가 같지만, `Random`은 1,000번의 반복 실행 동안 매번 다른 난수 피벗을 선택하므로 **1,000회 중 가장 불균형하게 분할된 시행의 최대 재귀 깊이(45단계)**가 `global_max_depth`에 기록되어 메모리 사용량이 가장 높게 나타났다.

## 5. 메모리 사용량의 측정 방법과 계산 기준

원본 데이터 배열(`original_arr`, `test_arr`)은 모든 알고리즘의 공통 공간이므로 제외하고, 각 정렬 알고리즘이 실행되는 동안 동시에 활성화되는 **동적 할당 힙(Heap) 메모리**와 **함수 호출 스택(Call Stack) 및 지역 보조 변수**의 최대 합산 크기(Byte)를 `sizeof` 연산자를 활용하여 계산하였다 (64비트 환경 기준: `sizeof(void*) = 8 Bytes`, `sizeof(int) = 4 Bytes`).

1. **힙 정렬 (`Heap Sort`)**
   - **측정 기준**: 반복문(Iterative) 기반의 `heapify`를 사용하여 재귀 호출이 발생하지 않으므로, 동시에 활성화되는 `heap_sort()` $\to$ `heapify()` $\to$ `swap()` 호출 체인의 매개변수 및 지역 보조 변수의 총합으로 계산하였다.
   - **계산식**:
     - `heap_sort`: 포인터 2개(`arr`, `comp`) + 정수 2개(`n`, `i`)
     - `heapify`: 포인터 2개(`arr`, `comp`) + 정수 5개(`n`, `i`, `largest`, `left`, `right`)
     - `swap`: 포인터 2개(`a`, `b`) + 정수 1개(`temp`)
     - $\text{Total Memory} = 6 \times \text{sizeof(void*)} + 8 \times \text{sizeof(int)} = 6 \times 8 + 8 \times 4 = \mathbf{80\text{ Bytes}}$

2. **병합 정렬 (`Merge Sort`)**
   - **측정 기준**: 동적 할당된 임시 배열(`temp`)의 크기와 `merge_sort_recursive` 함수의 최대 재귀 깊이(`global_max_depth`)에 따른 스택 프레임 누적 크기를 합산하였다[cite: 2, 4].
   - **계산식**:
     - 임시 배열 크기: $n \times \text{sizeof(int)} = 4n\text{ Bytes}$[cite: 4]
     - 재귀 1단계 스택 프레임(`MERGE_FRAME_SIZE`): 포인터 4개(`arr`, `temp`, `comp`, `max_depth`) + 정수 3개(`left`, `right`, `depth`) $= 4 \times 8 + 3 \times 4 = \mathbf{44\text{ Bytes}}$[cite: 2, 4]
     - $\text{Total Memory} = (n \times 4) + (\text{Max Depth} \times 44)\text{ Bytes}$
     - (예: $n = 20,000$, 최대 재귀 깊이 $16$일 때 $80,000 + 16 \times 44 = \mathbf{80,704\text{ Bytes}}$)[cite: 4]

3. **퀵 정렬 (`Quick Sort`)**
   - **측정 기준**: 추가 동적 배열 없이 제자리에서 분할하므로, 재귀 함수의 최대 호출 깊이(`global_max_depth`)에 단일 스택 프레임 크기를 곱하여 계산하였다[cite: 2, 4].
   - **계산식**:
     - 재귀 1단계 스택 프레임(`QUICK_FRAME_SIZE`): 포인터 3개(`arr`, `comp`, `max_depth`) + 정수 3개(`low`, `high`, `depth`) $= 3 \times 8 + 3 \times 4 = \mathbf{36\text{ Bytes}}$[cite: 2, 4]
     - $\text{Total Memory} = \text{Max Depth} \times 36\text{ Bytes}$
     - (예: $n = 20,000$, `Median3` 최대 재귀 깊이 $25$일 때 $25 \times 36 = \mathbf{900\text{ Bytes}}$)[cite: 4]

## 6. 종합 결론
실험 결과, 세 알고리즘 모두 시간 복잡도 $O(n \log n)$을 따르지만 내부 동작 방식에 따라 뚜렷한 트레이드오프(Trade-off)가 존재함을 확인하였다.
- **빠른 실행 속도**가 최우선인 일반적인 환경에서는 캐시 지역성이 뛰어나고 분할 균형이 잡힌 **퀵 정렬(Median-of-Three)**이 유리하다.
- **메모리가 제한된 임베디드 환경**이거나 최악의 경우에도 $O(n \log n)$ 시간 복잡도와 $O(1)$ 공간을 보장해야 할 때는 **힙 정렬**이 적합하다.
- **안정 정렬(Stable Sort)**이 필요하거나 최소한의 비교 횟수로 일관된 성능을 내야 할 때는 $O(n)$의 추가 메모리를 감수하더라도 **병합 정렬**을 선택하는 것이 효과적이다.
