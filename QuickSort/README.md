# [과제-12] 퀵 정렬의 피벗 선택에 따른 성능 비교 분석 보고서

---

## 1. 데이터 크기 증가에 따른 세 가지 퀵 정렬의 비교 횟수 변화

### 피벗 선택 방식에 따른 비교 횟수 측정 결과
| 데이터 크기 (N) | 첫 번째 원소 (First) | 무작위 원소 (Random) | 세 원소의 중앙값 (Median-3) |
| :--- | :--- | :--- | :--- |
| **1,000** | 11,752 | 12,047 | 11,200 |
| **2,000** | 27,156 | 26,169 | 25,002 |
| **4,000** | 57,923 | 59,734 | 54,076 |
| **8,000** | 128,907 | 132,026 | 120,120 |
| **16,000** | 287,902 | 268,615 | 257,440 |
| **20,000** | 343,679 | 355,634 | 325,256 |

데이터 크기($N$)가 1,000부터 20,000까지 증가함에 따라 측정한 결과, 세 가지 퀵 정렬 방식 모두 비교 횟수가 $O(N \log N)$의 수학적 비율을 따르며 증가하는 경향을 보였습니다. 
데이터 크기가 2배 증가할 때 비교 횟수는 단순 2배가 아니라 약 2.1~2.2배가량 증가하였으며, 이는 퀵 정렬의 평균 시간 복잡도 특성과 정확히 일치합니다. 전체 실험 구간에서 데이터 크기와 무관하게 항상 **세 원소의 중앙값(Median-of-Three) 방식이 가장 적은 비교 횟수**를 기록하여 우수한 효율을 입증했습니다.

## 2. 피벗 선택에 따른 성능 차이 (First, Random, Median-of-Three)

동일한 무작위 데이터를 기반으로 정렬을 수행했을 때, 피벗 선택 방법에 따라 다음과 같은 성능 차이가 발생했습니다.

* **세 원소의 중앙값 선택 (Median-of-Three)**
  전체 구간에서 가장 적은 숫자 비교 횟수를 기록했습니다. (N=20,000 기준 약 325,256회) 중앙값을 탐색하기 위해 매 분할마다 3회의 추가적인 비교 연산이 발생함에도 불구하고, 전체 분할 과정의 횟수 단축이 이를 압도적으로 상쇄하여 가장 뛰어난 성능을 보였습니다.
* **첫 번째 원소 (First) vs 무작위 원소 (Random)**
  두 방식의 성능은 특정 방식이 우위를 점하지 않고 데이터 크기에 따라 엎치락뒤치락하며 거의 유사한 비교 횟수를 기록했습니다. (N=20,000 기준 각각 343,679회, 355,634회) 

## 3. 피벗 선택 방법이 분할 결과와 비교 횟수에 영향을 미치는 이유

단순히 측정값이 차이 나는 것을 넘어, 이러한 성능 차이가 발생하는 근본적인 원인은 **퀵 정렬의 재귀 트리 깊이(Tree Depth)와 분할의 균형성**에 있습니다.

1. **분할 결과에 미치는 영향:**
   퀵 정렬의 총 비교 횟수는 '선택된 피벗이 배열을 얼마나 균등하게 반분(5:5)하는가'에 전적으로 달려 있습니다. 피벗이 전체 데이터의 실제 중앙값에 가까울수록 배열은 균등하게 나뉘며 재귀 트리의 깊이는 $\log N$에 수렴합니다. 반대로 최솟값이나 최댓값에 가까운 극단적인 값이 피벗으로 선택되면 배열이 1:(N-1)로 심하게 편향 분할되어 트리의 깊이가 최대 $N$까지 깊어집니다.
2. **First와 Random의 성능이 비슷했던 이유:**
   이론적으로 First 방식은 정렬된 데이터에서 최악의 성능($O(N^2)$)을 내고 Random 방식이 이를 보완하지만, 이번 실험은 `rand()` 함수로 생성한 **'완전한 무작위 배열'**을 사용했습니다. 배열 자체가 이미 완벽히 섞여 있기 때문에 첫 번째 위치의 값을 고르는 것과 난수 위치의 값을 고르는 것은 통계학적으로 완벽히 동일한 난수 추출에 해당합니다. 따라서 두 방식 간의 분할 퀄리티에 차이가 발생하지 않았습니다.
3. **Median-of-Three의 비교 횟수가 획기적으로 줄어든 이유:**
   양 끝값과 중앙값 중 중간 크기의 값을 피벗으로 삼기 때문에, 최솟값이나 최댓값이 피벗으로 선정되어 배열이 극단적으로 쪼개지는 최악의 분할(Worst Partition)을 원천적으로 차단합니다. 항상 5:5에 가까운 균형 잡힌 분할을 강제하므로 서브 배열의 크기가 빠르게 줄어들고, 파티션 함수 내부의 `while` 루프 반복 횟수(비교 횟수)가 누적 단위로 크게 감소하는 것입니다.

## 4. 효과적인 피벗 선택 방법 결론

실험 결과를 종합해 볼 때, 가장 효과적인 피벗 선택 방법은 **세 원소의 중앙값(Median-of-Three)** 방식입니다. 
무작위 피벗(Random Pivot) 방식은 난수 생성 함수 자체의 오버헤드가 발생하며, 여전히 재수가 없으면 극단적인 값이 선택될 확률이 통계적으로 존재합니다. 반면 Median-of-Three 방식은 단 3번의 상수 시간 비교($O(1)$) 연산만을 추가 투자하여 극단적 불균형 분할을 확실하게 방어해 냅니다. 데이터의 초기 상태(이미 정렬되어 있든, 무작위로 섞여 있든)에 흔들리지 않고 가장 안정적인 $O(N \log N)$ 성능을 보장할 수 있는 최선의 설계입니다.

## 5. [보너스] 재귀적 퀵 정렬과 반복적 퀵 정렬의 성능 비교

### 1) 100회 연속 실행 총 시간 비교 (N=10,000 / Median-of-Three)

| 구현 방식 | 총 실행 시간 (100회 누적) |
| :--- | :--- |
| **Recursive Quick Sort (재귀적)** | 193.0000 ms |
| **Iterative Quick Sort (반복적/스택)** | 136.0000 ms |

* **결과:** 반복적(Iterative) 방법이 재귀적(Recursive) 방법보다 실행 속도 측면에서 **약 30% 더 빠른** 우수한 성능을 보였습니다.

### 2) 성능 차이 발생 원인 분석
두 알고리즘은 분할(Partition)을 수행하는 논리와 횟수가 완벽하게 동일합니다. 그럼에도 실행 시간에서 큰 차이가 발생한 이유는 누적되는 **함수 호출(Function Call) 시스템 오버헤드** 때문입니다.

* **콜 스택 프레임 관리 비용:**
  재귀 방식은 매 분할을 수행할 때마다 시스템 스택 메모리에 현재 함수의 지역 변수, 매개변수, 반환 주소(Return Address)를 할당(Push)하고 종료 시 해제(Pop)하는 무거운 Context Switching 과정을 거칩니다. 반면 반복적 방식은 힙(Heap) 영역에 명시적으로 할당한 배열(스택)을 사용하여 단순히 두 개의 `left`, `right` 정수형 인덱스만 Push/Pop 하므로 메모리 오버헤드가 극히 적습니다.
* **CPU 파이프라인 효율:**
  재귀 방식의 잦은 `Call`/`Jump` 명령어는 CPU의 분기 예측 시스템(Branch Prediction)에 부담을 주어 파이프라인 지연을 유발합니다. 반복적 방식은 단일 `while`문 내에서 연속적으로 작업을 처리하므로 캐시(Cache) 히트율과 실행 효율이 높게 유지됩니다.
